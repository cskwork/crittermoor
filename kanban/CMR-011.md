## Description

Add a Hatchery structure. When two tamed critters of the same species are assigned to the hatchery, after 600 sim-ticks an Egg item appears in the hatchery. The egg hatches after another 600 ticks into a level-1 critter inheriting the parents' species + a re-rolled trait. Stochastic — both gates use the shared RNG.

- Test: deterministic happy-path produces an egg + a critter in expected ticks.
- Save v3+: Hatchery + Egg + breeding timers persist; v3 migration default empty.
- `npm test`, `npm run typecheck`, `npm run lint` green.

## Domain Brief

**What**: Define the world rules that govern a Hatchery building, its assigned parents, the egg it produces, and the level-1 critter it hatches — all deterministic against the shared seeded RNG.
**Why**: Breeding is the only renewable critter source short of taming; without it the colony cannot recover from losses, and any non-determinism breaks save/replay (the project's core contract).
**As-Is → To-Be**:
- As-Is: 6 structure kinds, no item entities, no breeding loop. Critters enter the colony only via `tryTame` at `src/game/Sim/Critters/tame.ts:24`.
- To-Be: 7 structure kinds (incl. `Hatchery`); a 2-phase per-Hatchery state machine (`incubating`→`hatching`) ticks against `sim.rng`; egg is a real ECS entity; hatchling is a Player-faction `Critter` with `Bond.level=20` and a re-rolled `CritterTrait`.

- Reuse the existing build pipeline verbatim — `STRUCTURES` table at `defs.ts:21`, `spawnBlueprint` at `Structures/spawn.ts:14`, and `construct` system at `systems/construct.ts:65` already complete any new kind purely from its `buildTicks`.
- Mirror the raid side-channel pattern (`systems/raid.ts:17-35`) for hatchery state: hide a `Map<hatcheryEid, HatcheryState>` on the `SimWorld` and expose `getHatcheries/setHatcheries` for the codec.
- Hatchling spawn = `spawnCritter(...,{level:1})` followed by the tame.ts:44-48 sequence (`Faction.Player` + remove `Wild` + add `Bond` with `level=20`).
- Save shape: extend `SaveDocV3` with optional `hatcheries?` + `eggs?` arrays; older v3 saves load with empty defaults (same approach `raid?` and `resources?` already use — no version bump required by AC wording "v3 migration default empty").
- RNG ordering risk: breeding RNG calls happen only when a Hatchery has both parents assigned, so untouched saves don't shift downstream rolls.
- No `Trait` component exists today (grep confirms); introduce a minimal `CritterTrait{traitId:ui8}` set only on hatchlings, with a 4-entry trait table.

- Additive optional fields on `SaveDocV3` keep older v3 saves loadable with zero migration code — the "v3 doc without `hatcheries` field loads with empty list" test is the cheapest regression to write for this pattern.
- Tick-order placement is part of the RNG determinism contract: `system_breeding` runs AFTER `sim.tick++` so "N runTicks since assign" equals "N ticks elapsed", matching the AC wording literally. Inserting an RNG-consuming system anywhere else would silently shift downstream draws.
- bitecs eid reuse on `removeEntity` is real: destroying the egg BEFORE spawning the hatchling on the same tick risks eid collision and breaks the codec eid-remap. The work-side ordering (`spawnCritter` then `removeEntity(egg)`) is load-bearing, not stylistic.
