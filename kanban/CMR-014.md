## Domain Brief

**What**: Map out how pause, Esc, save/load and settings already work so the next stage can add a menu with minimal change.
**Why**: Players cannot pause mid-game today; Esc only clears a tool. Adding a menu without understanding the existing scheduler/keybind/save wiring risks regressing speed control or save flow.
**As-Is → To-Be**:
- As-Is: pause is implicit (speed=0 in `useUiStore`); Esc clears tool; no `paused` flag; no settings store; Save/Load live only in HUD.
- To-Be: explicit `paused` flag on `useUiStore` gates `TickScheduler`; Esc opens/closes a `PauseMenu` modal that reuses existing save APIs and a new `useSettingsStore` persisted in `localStorage`.

Key facts the implementer must know before coding:

- `TickScheduler.tickLoop` reads `useUiStore.getState().speed` per frame (`src/game/Sim/TickScheduler.ts:33-45`). Extend its predicate to also check a new `paused` flag — do not mutate `speed` to fake pause, or the prior user-selected speed must be tracked and restored.
- `shouldIgnore` was hardened in commit `8d92182` (HIGH review fix) and now ignores key events whose target is a focused `<button>` (`src/app/Keybindings.tsx:15-22`). The Esc-to-open/close handler must run **before** `shouldIgnore` so PauseMenu buttons cannot trap focus and lock the menu open.
- Save/Load already works via `saveGame`/`loadGame`/`listSaves` in `src/game/Sim/Saves/store.ts:26-57` and the window globals `__crittermoorGame.sim` / `__crittermoorApplyLoad` set in `Game.newGame` (`src/game/Game.ts:64-70`). PauseMenu **must** reuse this bridge, not invent a new one. HUD's load list at `src/ui/screens/HUD.tsx:115-133` is the reference renderer.
- No `localStorage` usage exists in `src/` today; a fresh settings store needs hydration on construction and write-through on every set. Settings values are persisted only — no audio engine, autosave loop, or palette switcher is in tree yet (out of scope for this ticket).
- Vitest is wired for `.test.tsx` but `@testing-library/react` is **not** a dep. The AC ("opening menu sets sim.paused; closing resumes") reads as a store-level assertion — do not pull in RTL just for this.

## Plan Candidates

**What**: Three viable shapes for the pause-menu implementation.
**Why**: The biggest design choice is *where* the pause flag lives and *how* Esc replaces today's tool-clear; the rest follows.
**As-Is → To-Be**:
- As-Is: pause = speed=0; Esc = clear tool; no settings; no modal infra.
- To-Be: one of the options below.

- **A. `paused` on `useUiStore`, Esc replaces tool-clear, settings store new.** Touch: `uiStore.ts`, `Keybindings.tsx`, `TickScheduler.ts`, `PauseMenu.tsx`, `settingsStore.ts`, `App.tsx`, `Game.ts`, `tests/sim/pause.test.ts`. Smallest surface; drops the old "Esc clears tool" behaviour entirely.
- **B. Same as A but Esc stays layered: Esc clears tool first if `toolMode !== 'select' || selectedEid !== null`, otherwise opens menu.** Preserves muscle-memory tool-cancel but adds a branch + needs a test. Two-step Esc to reach menu when a tool is active.
- **C. Mutate `speed` instead of adding a `paused` flag (store prior speed in `pausedFromSpeed`).** Avoids touching `TickScheduler.ts`, but the AC explicitly names a `paused` flag and reviewers will flag the speed/pause coupling; restore-on-close becomes the new bug surface.

## Recommendation

**What**: Go with Option A — explicit `paused` flag on `useUiStore`, Esc swaps to open/close menu, new `useSettingsStore` persisted to `localStorage`.
**Why**: Matches the AC wording ("sim.paused") literally, keeps the speed knob untouched (no restore-on-close bug class), and stays inside the existing zustand + window-global patterns the HUD already uses. Option C trades a one-line scheduler change for a stateful speed-restore problem the AC actively warns against. Option B's layered-Esc is nicer UX but is not in the AC and inflates test surface.

**Risks accepted**: (1) the old "Esc clears tool" muscle memory is gone — call it out in the help bar; (2) settings sliders persist values that nothing currently consumes — acceptable per AC scope.

## Learnings

**What**: Three reusable facts the next ticket needs, plus one anti-pattern to keep on the rejected pile.
**Why**: Pause / Esc / settings overlap with future tickets (autosave loop, audio engine, palette switcher, any new modal) — saving the gotchas saves the next agent an Explore stage.
**As-Is → To-Be**:
- As-Is: pause was implicit (`speed === 0`); no wiki; future modals would re-discover the Esc/`shouldIgnore` interaction.
- To-Be: `docs/llm-wiki/ui-pause-and-scheduler.md` + `docs/llm-wiki/settings-store-persistence.md` capture the invariants.

- Esc handler must run **above** `shouldIgnore` in `Keybindings.tsx`. `shouldIgnore` (commit `8d92182`) blocks key events on any focused `<button>` — putting Esc below it traps the menu open once the user clicks any button. Any future modal-close key needs the same exemption.
- `paused` and `speed` stay independent. Option C (mutate `speed`, store `pausedFromSpeed`) is permanently rejected — it forces a restore-on-close handler which is a recurring bug source in similar codebases. The AC wording (`sim.paused`) already implies a flag, but the rationale is wider.
- `localStorage` writes go through a try/catch wrapper plus a `typeof localStorage === 'undefined'` guard. Both layers are intentional: `undefined` covers SSR-ish test harnesses; try/catch covers private-browsing `SecurityError` and quota errors. A single guard isn't enough.
- Settings sliders are persisted but **not yet consumed**. Future tickets (audio engine, autosave timer, palette renderer) must read `useSettingsStore` rather than re-introducing their own preference store.
