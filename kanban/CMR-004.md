## Description

Add a weather system that cycles through {clear, rain, storm} on a seeded schedule (~1 weather change per in-game day). Weather is a single sim-wide value with a tinted Pixi overlay on the renderer and gameplay effects:

- rain: chop/mine -5% speed, fire-type moves -20% power, food/forage +0% (neutral)
- storm: pawn move -10%, turret accuracy -25%, raid scheduler pauses

## Acceptance Criteria

- New `Weather` enum + `SimWorld.weather` + `weatherTicksRemaining`; advance in `time.ts` system using shared RNG.
- Renderer overlay (semi-transparent blue for rain; darker grey + lightning flicker for storm).
- Battle damage formula multiplies fire-type effective power by 0.8 during rain.
- Turret accuracy multiplier hooked in `turret.ts`.
- Save v4 migration adds weather state (with a no-op v3->v4 migration in `migrations.ts` + fixture round-trip test).
- Test: deterministic weather schedule from a fixed seed; rain reduces fire move damage.
- `npm test`, `npm run typecheck`, `npm run lint`, `npm run build` all green.

## Domain Brief

**What**: Add a sim-wide weather state (clear / rain / storm) that flips ~once per in-game day and tweaks battle, turret, raid, and renderer behaviour.
**Why**: Today the world has day/night colour but no weather; battles are uniform and raids never relent. Weather adds a deterministic environmental rhythm without changing systems' architecture.
**As-Is → To-Be**:
- As-Is: `sim.weather` does not exist; `system_time` is a stubbed placeholder; the renderer only tints for night; battle / turret / raid ignore environment.
- To-Be: `SimWorld.weather` + `weatherTicksRemaining` advance in `system_time` from `sim.rng`; renderer paints a fullscreen tint; rain cuts Fire-move power ×0.8; storm makes turrets miss 25% and pauses raid scheduling. Save format moves to v4 with a no-op default.

- `system_time` at `src/game/Sim/systems/time.ts:19-21` is a literal "placeholder for time-based triggers (weather, raids)" — we own that slot.
- Tick order (`src/game/Sim/tick.ts:24-37`) runs `time` second; turret/raid/battle read `sim.weather` later in the same tick, so flipping at the top of tick is correct and bit-stable.
- `computeDamage` (`src/game/Sim/Battle/damageFormula.ts:13-41`) is pure; it gains an optional `weather` arg threaded by `executeTurn` (`BattleSim.ts:8-92`), whose only production caller is `Game.ts:111` where `this.sim.weather` is in scope.
- `system_turret` (`src/game/Sim/systems/turret.ts:47-54`) gains a `sim.rng.chance(0.75)` gate before damage when storm — one extra draw per shot, kept deterministic by living inside the existing per-target loop.
- `system_raid` (`src/game/Sim/systems/raid.ts:39-40`) early-returns on storm and does NOT advance `nextRaidTick`, so raids resume the tick storm ends. No RNG drawn while paused.
- `Renderer` already mirrors a fullscreen `nightTint` Graphics on `app.stage` (`Renderer.ts:31-32, 87-100`); we add a sibling `weatherTint`. Storm lightning flicker derives purely from `sim.tick` (no out-of-tick RNG draw).
- Save format: append `SaveDocV4` to the schema chain (`Saves/schema.ts:39-50`), bump `SAVE_VERSION` to 4, add `v3ToV4` no-op default in `migrations.ts:6-13` — same shape as the existing `v2ToV3`.
- Determinism contract: weather rolls (one `int(3)` for kind + one duration draw) live in `system_time` so they precede every other consumer in the tick; the RNG sequence stays invariant when weather flips mid-day.
- Out-of-AC: the Description mentions chop/mine -5% and pawn-move -10%, but the AC and "Files likely touched" list omit `jobs.ts` and `pathFollow.ts`. We ship the AC subset and leave those for a follow-up ticket (noted in Recommendation).

## Plan Candidates

**What**: Three implementation shapes for the weather system. Each names the seam it touches and what it costs to maintain.
**Why**: Choice determines blast radius, save format risk, and how weather is consumed across sim systems and the renderer.
**As-Is → To-Be**:
- As-Is: No weather state, no save migration, no battle/turret/raid coupling to environment.
- To-Be: One of A/B/C below — chosen in Recommendation.

- **A — Plain SimWorld field + positional args (chosen).** Add `weather` + `weatherTicksRemaining` as direct fields on `SimWorld`; advance in `system_time` via `sim.rng`. `computeDamage` and `executeTurn` gain an optional `weather` arg with default `Clear`. `system_turret` and `system_raid` read `sim.weather` directly. Renderer mirrors `nightTint` for a `weatherTint`. Save v3→v4 no-op default. Touches: 8 src files + 3 test files. No new abstraction.
- **B — ECS component `Weather` on a singleton entity.** Reuses bitecs query patterns and avoids polluting `SimWorld`. Costs: a fake "world meta" entity, a `defineQuery([Weather])` that returns 1 row, and ceremony in every reader. No reuse benefit because there is exactly one weather and zero queries that mix it with other components. Still needs save v4 to persist the eid.
- **C — Description-complete bundle (A + jobs/move multipliers).** Ships A plus modifying `WORK_TICKS_CHOP/MINE` and `STEP_INTERVAL` so chop/mine -5% during rain and pawn-move -10% during storm match the Description bullets. Adds 2 more touched files (`jobs.ts`, `pathFollow.ts`) outside the AC's "Files likely touched" list and outside the AC test contract. Higher blast radius and broader review surface for flavour effects the AC does not bind.

## Recommendation

**Why**: Matches the AC and "Files likely touched" list verbatim, reuses the `nightTint`, `v2ToV3`, `phaseOf` and `chance/int` patterns 1:1, and keeps save migration to a literal field-default. No new abstractions.
**As-Is → To-Be**:
- As-Is: `system_time` is empty; weather is unrepresented anywhere.
- To-Be: `sim.weather` flips on a seeded schedule and is read by turret, raid, battle, and renderer.

- Risk accepted: the Description bullets for chop/mine -5% and pawn-move -10% ship as a follow-up; flag in QA evidence so the omission is intentional, not missed.

## Learnings

**What**: Four durable facts captured from shipping the weather system.
**Why**: Future tickets touching battle/turret/raid/renderer/saves should not have to re-derive these.
**As-Is → To-Be**:
- As-Is: weather-related invariants live only in `## Plan` and the implementation diff.
- To-Be: codified in `docs/llm-wiki/{weather-system,save-version-migration}.md` for re-use.

- One sim-wide field beats an ECS singleton for "exactly one" world state. The bitecs query ceremony pays no dividend when there is no second-component join — confirmed in `## Plan Candidates` (Option A vs B).
- Optional positional args with `= Weather.Clear` defaults are a safe seam for threading new sim context through pre-existing pure functions; the existing battle determinism test passed without modification.
- Pre-existing eslint baseline failures in tooling/template directories can block QA gates. `.eslintrc.cjs` `ignorePatterns` is the right escape hatch — not source-edits in `skills/`.
- Storm-pause-without-RNG-advance is a deliberate gameplay surprise: raids fire the tick after the storm ends, so a long storm has no rolling raid backlog. Worth flagging to future game-design tickets.
