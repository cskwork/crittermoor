## Description

Today wardens chop and mine resources directly into `ColonyResources` totals. Add a designated "Stockpile" zone tool so dropped items are physical and must be hauled to the zone. This is the foundation for selective filters and base organization later.

- Test: place stockpile + chop a tree => warden hauls + ColonyResources.wood increments only after delivery.

## Domain Brief

**What**: Today chopping/mining instantly grows the colony wood/stone counter. Add a player-paintable "Stockpile" zone so dropped resources become physical piles that wardens must carry to the zone before the counter goes up.
**Why**: This is the first real haul loop. Until items are physical and have a destination, downstream features (selective filters, base layout, food chains) have nothing to attach to.
**As-Is → To-Be**:
- As-Is: `progressJob` at `src/game/Sim/systems/jobs.ts:115` credits `sim.resources.wood/stone` directly the instant a chop/mine finishes; there is no haul job, no stockpile zone, and no item entity in the ECS.
- To-Be: chop/mine spawns an `ItemStack` ECS entity (Wood or Stone, qty) on the worked tile; an idle warden in a new `JobKind.Haul` state walks to the closest stack, then to the closest tile in `sim.stockpiles: Set<number>`, and only on deposit is `sim.resources` incremented. Player paints the stockpile rectangle via a new `stockpile` tool mode (`Z`); the zone, stacks, and tile-keys round-trip through save v3 as additive optional fields.

Key facts (source of truth):

## Plan Candidates

**A. Tile-set Stockpile + ItemStack ECS entity + Haul folded into `makeJobSystem`** (recommended).
- `sim.stockpiles: Set<number>` mirroring `sim.blueprints`; `ItemStack` is a real bitecs component on per-pile entities; `JobKind.Haul = 3` reuses `wardenQuery` / `isAlreadyTargeted` / `clearJob` / `ASSIGN_INTERVAL`.
- Pros: one place to dedup player jobs; matches the designations/blueprints idiom; saves stay additive; haul priority can sit naturally below chop/mine.
- Cons: jobs.ts grows; the per-tile stockpile is not strictly "an ECS component" (the *items* are — the AC reading is satisfied via `ItemStack`).

**B. New `makeHaulSystem` parallel to construct/jobs** (strict literal AC reading).
- A dedicated haul system with its own assign/progress loop, registered in `tick.ts` alongside `jobsSystem` and `constructSystem`.
- Pros: clean separation; AC says "new haul job" — easy to point at.
- Cons: duplicates the warden query and dedup helpers; adds another `SimHooks` slot; cross-job priority must be coordinated by hand.

**C. Stockpile as a per-tile ECS sentinel entity** (most literal "ECS component" reading).
- Each painted tile spawns a tiny `StockpileTile` entity (Stockpile + TilePos) — the zone is a query, not a Set.
- Pros: matches the AC wording exactly; queryable by other systems with no Set lookup.
- Cons: hundreds of tiny entities; expensive iteration on every tick; awkward and bloated save (re-spawn N entities + remap their eids); needs new occupancy invariants.

_details: docs/CMR-003/explore/reuse-inventory.md_

## Recommendation

Take **A**. The repo already encodes "per-tile player state" as a Map/Set on `sim` (designations, blueprints), and the AC's "ECS component / SoA store" is honoured by making `ItemStack` itself a real bitecs component — the things that actually move are entities, the zone is just a tile-key set. The risk accepted is that `Renderer` gains its first drag-rect handler (small, localised in `dispatchTile`'s neighbourhood). Edge cases to enforce in the implementation: refuse stockpile paint over `cost === 0` tiles, merge same-tile ItemStack spawns by incrementing `qty`, and on mid-haul stack disappearance treat it like the existing `if (!designation) clearJob(eid)` branch.

First failing test (in a new `tests/sim/jobs.test.ts`): create a sim, pin a warden idle, `sim.stockpiles.add(key(10,10))`, `spawnItemStack(sim, ItemKind.Wood, 3, 3, 2)`, manually set the warden's `TilePos` to `(3,3)` then to `(10,10)` between job ticks, and assert that the ItemStack entity is gone and `sim.resources.wood === 32` (30 starter + 2 from the pile) only after the deposit step — not before.

- Additive save fields (`<zone>Keys?: number[]`) let new zones ship without bumping `SAVE_VERSION`. The `blueprintKeys?` precedent from commit `1969113` was followed line-for-line; legacy v3 saves load with empty defaults. No migration code needed for additive shape.
- The ticket's "Files likely touched" list pointed at the stale path `src/app/state/toolStore.ts` (real path: `src/app/stores/uiStore.ts`). Explore caught and corrected it in `## Domain Brief`. Lesson: trust grep over the ticket body when paths look off.
