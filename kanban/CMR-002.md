## Description

Stoves currently render but do nothing. Add a `cook` job that consumes 2 wood from colony resources and turns it into 1 "meal" (stored as `ColonyResources.meals`). Wardens with cookSkill >= 1 should auto-pick the job when there is at least 1 active blueprint-completed Stove and `meals < 5`. The Stove must remain available (the warden returns to it for the next batch).

Meals are consumed when a warden eats (lowering Needs.hunger).

## Acceptance Criteria

- `ColonyResources` gains a `meals: number` field with starter 0; rendered in the Resources HUD next to wood/stone.
- New cook job in `src/game/Sim/systems/jobs.ts` plus a `makeCookSystem` that runs each tick: idle warden -> walk to nearest completed Stove (use existing path worker) -> stand for cookTicks (4 ticks default, -1 per skill level, min 1) -> deduct 2 wood, add 1 meal, log event.
- Warden "eat" behavior in `src/game/Sim/systems/behavior.ts` prefers meals (decrement `meals`, restore hunger by 60) before falling back to raw forage.
- Save schema v3 already serializes ColonyResources; ensure the new `meals` field is set on load (default 0 for legacy v3 saves missing the key).
- Test `tests/sim/jobs.test.ts`: warden with cookSkill=2 + a Stove + wood=10 produces 1 meal after expected ticks and consumes 2 wood. Determinism preserved.
- `npm test`, `npm run typecheck`, `npm run lint` all green.

## Learnings

**What**: Capture the surprises and contract notes that future producer/consumer tickets should not have to rediscover.
**Why**: This was the first economy loop in the codebase — every later loop (smelt, brew, bake) will copy this contract or break it.
**As-Is → To-Be**:
- As-Is: No prior wiki coverage of cook/eat or producer-consumer pairs; assumptions only in the ticket body.
- To-Be: `cook-economy-loop` captures the pattern (race guard, helper exports, schema-stable backfill) plus three open follow-ups.

- The plan's 64-tick first-failing-test budget was wrong: with `cookSkill = 2` and `ASSIGN_INTERVAL = 4`, the warden completes a cycle every ~12 ticks and would cycle to `meals == 5` long before the assertion ran. **Future loops:** size the test budget to "exactly one cycle plus one ASSIGN_INTERVAL slack", not to "a comfortable margin".
- `isAlreadyTargeted(sim, key, ignoreEid)` keys on `Job.targetEid`. Chop/mine store designation keys (`ty*width + tx`) in the same field, so on small maps an entity id could numerically collide with a designation key and one warden could spurious-skip an assign tick. Effect today is bounded (one-tick skip); flagged as a refactor when a third producer arrives.
- Save schema can absorb a new resource field **without bumping the version** when the field has a sensible default (`?? 0` in `Saves/codec.ts`, `meals: 0` in `migrations.ts::v2ToV3`). Bumping to v4 was unnecessary and would have invalidated existing v3 saves.
- `clearJob` was duplicated locally inside `cook.ts` to avoid a cyclic import (cook → jobs → cook). Same reasoning applies to `HUNGER_PER_MEAL = 60` in `behavior.ts:19` — duplicate the constant rather than reverse the dep direction. **Rule of thumb:** never let a consumer system import from its producer; the consumer just reads `sim.resources`.
- Scope expansion (`.eslintrc.cjs` `ignorePatterns += 'skills'`) was needed because the lint AC ran against an untracked host-backed symlink. Recording the expansion in `## Scope Expansion` rather than silently extending the diff kept the Review trail honest. **Future:** if Symphony scaffolding ever moves in-tree, revisit the ignore.
