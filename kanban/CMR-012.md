## Description

Today the player sees the whole map. Add a fog layer that hides tiles outside any warden's vision radius (default 8) until first reveal; explored-but-out-of-LOS tiles render at 50% brightness. Wild critters in unrevealed tiles are not drawn.

## Acceptance Criteria

- New `Fog` Uint8 grid: 0 unseen, 1 explored, 2 visible. Updated each tick from warden positions.
- Renderer dims unexplored = black, explored = 50% darken, visible = full color.
- Wild critter sprites skipped on tiles where Fog != 2.
- Save v4 (or piggy-back on weather v4): persist Fog with simple RLE.
- Tests: vision radius math + fog persistence round-trip.
- `npm test`, `npm run typecheck`, `npm run lint` green.

## Domain Brief

**What**: Map out where a per-tile fog grid plugs into the existing sim, renderer, and save format so the implementer knows the surface area before touching code.
**Why**: Today every tile is visible — the game has no exploration tension and reveals wild critter positions for free. Acceptance ties together a sim grid, a render pass, and a save bump that must move together.

- To-Be: `TileMap.fog: Uint8Array` updated each tick from warden positions; renderer applies per-tile dim/black; Wild sprites suppressed off-visible; save v4 with RLE-encoded fog and a `v3ToV4` migration.

Key facts (full citations in `docs/CMR-012/explore/notes.md`):
- SimWorld is `src/game/Sim/world.ts:26-37` (lowercase `world.ts`, not `SimWorld.ts` as the ticket implied). `TileMap` already follows the dense-Uint8Array convention at `world.ts:8-13`.
- Warden query pattern: `defineQuery([Pawn, FactionComp, TilePos])` filtered by `FactionComp.id === Faction.Player` — used at `systems/jobs.ts:20` and `systems/construct.ts:9`. Reuse for fog reveal.
- Wild gate: `hasComponent(sim.ecs, Wild, eid)` — exactly the `systems/turret.ts:36` idiom. `EntityLayer.refFor` (`src/game/Renderer/EntityLayer.ts:59-74`) currently does not probe `Wild` and must learn to.
- Save chain: schema/migrations/codec at `src/game/Sim/Saves/{schema.ts,migrations.ts,codec.ts}` follow a clean `vN → vN+1` registry — append `SaveDocV4` + `v3ToV4`. Existing `b64encode` (`codec.ts:194`) is the obvious RLE-bytes sink.
- Acceptance says "vision radius 8" — use Euclidean squared (`dx*dx + dy*dy <= R*R`), matching `turret.ts:42`. Ticket title mentions "line-of-sight" but acceptance specifies only radius; raycast is out of scope.
- Fog never downgrades 1→0; only 0→{1,2} or 2↔1. Document this invariant in tests.

## Plan Candidates

**What**: Three concrete ways to wire fog into the sim and renderer; each names the files it touches and the test it adds.
**Why**: Acceptance criteria pin the data model and persistence shape but leave room on the render side — picking the right rendering structure now avoids rework after Review.
**As-Is → To-Be**:
- As-Is: No fog code anywhere; greenfield decision on layer structure.
- To-Be: One option chosen with reasoning; implementer follows the recipe without re-deliberating.

- **A — Inline fog overlay inside TilemapView.** Add a second `Graphics` per chunk in `TilemapView` keyed by a fog hash. Pro: one chunked layer to invalidate. Con: couples sim state into a class that is supposed to be terrain-only; harder to reason about. Tests: same as B.
- **B (recommended) — Dedicated `FogLayer` Container + `systems/fog.ts` + save v4 with RLE.** Mirrors the existing `TilemapView` chunked-hash pattern but in a separate Container drawn above `EntityLayer` and below the designation `overlay`. Pro: clean separation, easy to disable via debug flag later, matches existing one-class-per-layer style. Con: one extra Pixi Container. Tests: vision-math unit + save round-trip + v3→v4 migration in `tests/sim/fog.test.ts`.
- **C — Naive full-canvas fog repaint each tick (no chunking).** Simplest possible: one `Graphics`, clear+repaint every frame. 9216 rects on a 96×96 map. Pro: trivially correct. Con: breaks the repo's chunked-render style; risks frame-drop once map grows or weather/lighting stacks.

## Recommendation

**What**: Pick option B — a dedicated `FogLayer` plus a sim system and save v4 with simple RLE.
**Why**: It mirrors the existing `TilemapView` chunked-hash idiom (`TilemapView.ts:76-125`), keeps fog state out of the terrain class, and produces the smallest blast radius on Review. Risks accepted: one extra Pixi Container and one extra save version.
**As-Is → To-Be**:
- As-Is: No chosen direction; three candidates open.
- To-Be: Implementer writes `systems/fog.ts`, `FogLayer.ts`, `v3ToV4` migration, RLE codec helpers, and a Wild-gate in `EntityLayer.refFor` — then green tests.

## Learnings

**What**: Distilled what CMR-012 taught about per-tile UX state, vision math, save versioning, and the Symphony-symlink lint trap.
**Why**: Future fog/weather/lighting work and every new save field will retrace these steps — surfacing the surprises now keeps the next ticket from re-deriving them.
**As-Is → To-Be**:
- As-Is: The fog state machine, RLE codec, vision-radius metric choice, and symlink-lint regression lived only in this ticket's body — invisible to the next implementer.
- To-Be: Two wiki entries plus four learnings cite the exact `path:line` evidence so the next caller picks the right metric, the right codec shape, and the right ESLint posture on first try.

- "Vision radius 8" in the acceptance carries no metric. The team picked Euclidean inclusive (`dx*dx + dy*dy <= R*R`) to match `src/game/Sim/systems/turret.ts:33,42`. The ticket title's "line-of-sight" wording does NOT extend to raycast against walls — acceptance specified only radius. Future LOS tickets must claim their own ground, not assume CMR-012 covered it.
- Symphony's tracked symlinks at the repo root (`skills`, `.claude`, `docs/symphony-prompts`) walk into ESLint by default and broke `--max-warnings=0` after the wip commit landed. Fixed at `.eslintrc.cjs:19` ignorePatterns; future hook/agent/config edits must keep these exclusions. Rewind 1 ran specifically to land this single-line config fix.
- CMR-012 bumped `SAVE_VERSION` to `4` for the fog Uint8Array even though the wiki's `save-v3-additive-fields` rule would have allowed staying on v3 with `fog?: string`. The bump was driven by acceptance text ("Save v4 (or piggy-back on weather v4): persist Fog with simple RLE"), not by the no-bump rule failing — document the precedent so the next persisted-binary field follows the same path and the wiki conflict is acknowledged.
- Fog is a UX layer only. The invariant lives as a comment at `src/game/Sim/systems/fog.ts:9-10`. If a later ticket has AI/jobs/AStar read `sim.map.fog`, the read is a contract violation — escalate via code review, do not silently allow it.
